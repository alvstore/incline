- Zoho direct OAuth secrets stay in service-role `zoho_direct_credentials` (via `zoho-oauth`); `settings.zoho_mode` is the kill switch and direct needs a passed test, so a broken login never silently stops sync.
- `access_logs.payload` stores scan metadata only, never camera frames or device tokens: every writer (mips-webhook-receiver, reconcile-mips-pass-records, any future importer) passes the raw event through `_shared/mipsPayload.ts#stripScanMedia` before insert, and `prune_access_log_media()` (called from `maintain_log_sizes()`) strips any oversized value older than a day — inline base64 made this one table 85% of the database and every feed load a multi-MB download.
- Member gate check-ins pass the hardware scan time (`member_check_in._at`, honoured only for internal callers, max 48h old, never future); never stamp attendance with arrival/poll time, because outage backlogs would pile up at reconnect time.
- Automation worker calls use a shared response deadline under waitUntil; transport failures stay unknown and are never immediately retried. Nurture limits AI candidates and stops starting new work at its elapsed budget, leaving remaining candidates for scheduled runs.

- MSG91 sends only synced templates (registered via owner/admin/manager `msg91-templates`, content hash must match) with ordered ##VARn## and fail closed; DLT approval stays in SmartPing, because MSG91 registration is not operator approval.
- Website Lead Chatbot is deterministic (no public AI endpoint) and posts to `capture-lead` with `intake_type='website_chatbot'` (email required, interest from active plan names/categories, visit preference gated by submission_id); logic lives in `_shared/websiteLeadCapture.ts` (dedupe, fill-only-empty, slug-only branch, rate limit). Visitors stay in the website chat — no WhatsApp links/consent; only escalation is tel: for group/persistent discount asks — and chatbot leads pass `suppress_lead_welcome`. Post-capture answers come from `ai_knowledge` rows tagged `web:<topic>` (`_shared/websiteConcierge.ts`, shared with the WhatsApp AI's knowledge) and every turn is stored as a read-only `web_chat` inbox thread keyed by a synthetic `+00…` number marked do_not_contact (`_shared/websiteChatStore.ts`), so no worker can message it. The chatbot serves leads only: when `capture-lead` returns `already_member` (any profile phone — members, trainers, staff) the widget ends in a no-chat `handoff` step offering the WhatsApp self-service menu (wa.me/918298293003, shown only to registered numbers) or tel:, mirroring whatsapp-webhook's member gateway vs Ananya lead split.
- Chat pricing (website + WhatsApp leads) runs only through `_shared/salesPricing.ts` (stage ladder, live plan list, leak guard, one live link per lead+plan+amount in `sales_payment_links`, audit in `sales_quote_events`); the LLM never states amounts, so prices cannot be invented.

- In-App delivery: a `notifications` row (via dispatchCommunication) fans out through `web-push` to every device in `web_push_subscriptions` (kind web|fcm; Flutter registers with `register_device`).
- Campaign In-App delivery retains full audience filters, uses recipient-scoped board access and atomic leased jobs through `process-inapp-delivery`/Automation Brain; notification-level dedupe survives interrupted dispatch so scheduled and immediate delivery cannot diverge.
- Contract signing links resolve server-configured public HTTPS origins; request-origin fallback is published-host allowlisted and never local/preview, because signing invitations leave the browser.
- Contract PDF photos come only from the linked profile's display avatar in this backend's avatars bucket; embed image bytes and retain cached signed artifacts, so arbitrary URL fetches and changing gate identities cannot alter signed copies.
