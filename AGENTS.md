- Privileged (SECURITY DEFINER) functions used only by scheduled jobs, triggers or backend functions must have EXECUTE revoked from PUBLIC/anon/authenticated and granted to service_role only — signed-in users could otherwise call them directly.
- New functions in `public` are closed by default (migration 0018 revoked default EXECUTE for PUBLIC/anon/authenticated on postgres-owned functions): every migration that adds a function the app or an RLS policy calls must `GRANT EXECUTE ... TO authenticated` explicitly, and every SECURITY DEFINER RPC must contain a permission check (`rpc_guard_applies()` + `assert_branch_staff()`/`is_own_member()`/`has_role()`), otherwise `scripts/check-definer-guards.ts` fails CI — a privileged function without a visible check is how a member reaches other members' data.
- Direct-entry guards use `rpc_guard_applies(function_name)` (reads `request.path = /rpc/<fn>`, skips service-role/no-JWT, triggers, nested definer calls and Storage/Realtime policy evaluation) so authorization is enforced only where a user calls the RPC directly — nested internal calls keep working without duplicated checks.
- Extensions live in the `extensions` schema (pg_trgm, vector moved there; pg_net is not relocatable): functions using vector/trgm operators must pin `SET search_path = public, extensions` so operators resolve while keeping the schema fixed.
